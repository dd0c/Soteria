Installation guide

From a fresh RHEL 9, RHEL 10 or Debian 13 server to active monitoring in about ten minutes.

1. Before you install

  • A trusted starting point. The first baseline records the host as it is when you approve it. Install on a freshly built or verified host, not on one you suspect.
  • auditd reports program executions. It is installed by default on RHEL. On Debian: sudo apt install auditd. Without it everything except execution monitoring works.
  • Disk: about 600 bytes per monitored file (15 MB for 25,000 files) plus events for the retention period, 90 days by default.
  • Root access (sudo) and an x86_64 system with systemd.

2. Download and check the packages

Download the packages for your distribution and SHA256SUMS from the latest release, then check them:

sha256sum --check --ignore-missing SHA256SUMS

Every listed file you downloaded must report OK. Do not install a package that fails the check.

3. Install the package

RHEL 9

sudo dnf install ./soteria-<version>-1.el9.x86_64.rpm \
                 ./soteria-selinux-<version>-1.el9.noarch.rpm

RHEL 10

sudo dnf install ./soteria-<version>-1.el10.x86_64.rpm \
                 ./soteria-selinux-<version>-1.el10.noarch.rpm

soteria-selinux confines the daemon with an SELinux policy. Install it whenever SELinux is enabled (the default).

Debian 13

sudo apt install ./soteria_<version>_amd64.deb

The AppArmor profile is loaded automatically when AppArmor is enabled.

What the package does

  • creates the system account soteria, without a login shell;
  • installs /usr/bin/soteria, the soteria.service unit, the configuration /etc/soteria/soteria.toml, the audit rule /etc/audit/rules.d/soteria.rules and the SELinux or AppArmor policy;
  • creates /var/lib/soteria and /var/log/soteria;
  • loads the audit rule if auditd is running.

The package does not start monitoring. Initialization is a deliberate step, so that you approve what is recorded.

If you install auditd after Soteria, load the rule with sudo augenrules --load.

4. Review the configuration (optional)

The defaults monitor system binaries and libraries, /etc, /boot, persistence locations (SSH keys, shell startup files, systemd units, cron) and Soteria's own files. Common changes in /etc/soteria/soteria.toml:

SettingPurpose
[paths] include, excludeAdd application directories such as /opt/app, leave out noisy ones
[execution] unusual_pathsWhere running a program is suspicious (/tmp, /dev/shm, ...)
[alerts]Minimum severity, email and webhook delivery
[general] event_retention_daysHow long events are kept

Check every change:

sudo soteria config validate

Invalid configuration stops the service rather than letting it run with weaker defaults.

5. Initialize and approve the baseline

sudo soteria init

init checks prerequisites, creates the database and the baseline signing key (/etc/soteria/keys/baseline.key, readable by root only), inventories the host (10 to 60 seconds on a typical server) and shows the draft baseline: objects by kind and any coverage gaps.

Review it and answer y to approve. Approval signs the baseline with the root-held key. The daemon only has the public key, so it cannot forge an approval.

To review and approve later, for example in automation:

sudo soteria init --non-interactive    # leaves draft 1
sudo soteria baseline review 1
sudo soteria baseline approve 1

6. Start monitoring

sudo systemctl enable --now soteria
soteria status
sudo soteria verify

status should show Protection: ACTIVE. Anything else is explained by the sensor list and by soteria verify, which names every coverage gap, such as an unloaded audit rule or paths the daemon cannot read.

7. Check that it works

Create a harmless file in a monitored directory, then look for the alert a few seconds later:

sudo touch /etc/soteria-test
soteria alerts list
soteria alerts show <id>

Remove the file, close the alert with a note, and confirm nothing else deviates from the baseline:

sudo rm /etc/soteria-test
sudo soteria alerts close <id> --note "installation test"
sudo soteria scan --baseline

8. Forward alerts (recommended)

An attacker with full root access can tamper with anything stored on the host. Forward alerts by email or webhook so they leave the host as they happen: configure [alerts] as described in the command reference, validate, and restart the service:

sudo soteria config validate
sudo systemctl restart soteria

Changes to Soteria's own configuration raise a critical SELF-001 alert by design. Once you have confirmed the change, approve a new baseline (next step).

9. After maintenance: approve changes

Baselines are never updated automatically. After package updates or configuration changes:

sudo soteria scan --baseline              # what differs from the approved baseline
sudo soteria baseline create              # draft from the current state
sudo soteria baseline diff <approved> <draft>
sudo soteria baseline approve <draft>

10. Upgrade

Install the newer package the same way as in step 3. Your configuration and rules are kept and a running daemon is restarted. If the database format changes, the daemon first copies the database to /var/lib/soteria/soteria.db.schema-<N>.bak.

To go back: stop the service, install the previous package, and restore the copy:

sudo systemctl stop soteria
sudo cp /var/lib/soteria/soteria.db.schema-<N>.bak /var/lib/soteria/soteria.db
sudo chown soteria:soteria /var/lib/soteria/soteria.db
sudo systemctl start soteria

11. Remove

sudo dnf remove soteria soteria-selinux    # RHEL
sudo apt remove soteria                    # Debian

Removal stops the service and removes the program, but keeps the database, baselines, keys, rules and logs. To delete them deliberately:

sudo rm -rf /var/lib/soteria /etc/soteria /var/log/soteria
sudo userdel soteria
sudo rm /etc/audit/rules.d/soteria.rules && sudo augenrules --load

Troubleshooting

SymptomCheck
Service fails with exit code 3sudo soteria config validate
Service fails with exit code 5sudo soteria init was not run
Execution sensor unavailableIs auditd running? sudo augenrules --load
Kernel sensor degraded/proc/modules unreadable (containers)
inotify watch limit reachedRaise fs.inotify.max_user_watches with sysctl
SELinux denialssudo ausearch -m avc -c soteria, then report them

Logs: journalctl -u soteria. Full details are in the administration guide.
